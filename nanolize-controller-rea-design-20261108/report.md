# Nanolize：Agent 自主重构改造报告

设计版本：2026-11-08 / v1.1（修正 Graphify 与知识包术语）。本文合并中间流程自主化方案、工具拆分方案、运行成本讨论及 REA 设计借鉴。**本文是建议实施的设计，不是已完成的软件变更或性能实验报告。**

分析基线：nanolize `main@8c0745a19c40aa7673b28ceeb1b49c7ae2850d78`；参考项目 REA `main@72d5e72e6d7b7997c4ecb11972fc405be8ec67d2`。后续实施应重新确认目标 main 的差异。源码定位均绑定这些版本。

## 01 · 决策摘要 {#overview}

建议保留 Discover、Select Scope、Deliver 的产品形式，将原来第 3–7 步的执行策略交给 agent。系统继续提供稳定的工具、真实的测量结果、版本记录和资源管理。Agent 根据目标仓库决定先做什么、怎么拆分、何时验证、如何修复，以及什么时候可以交付。

核心目标是适应不同仓库，减少固定流程造成的阻塞与返工。自主化不自动等于更快、更便宜，也不降低“不删功能”等用户要求。是否改善成本，需要在相同条件下比较完整任务。

| 保留 | 改变 | 继续由程序保证 |
| --- | --- | --- |
| Graphify 功能图、nanolize 私有行为知识包、功能选择页面、Submit、报告网页 | 契约补充、基线运行、任务设计、重构、验证、修复、测量的顺序和组合 | 真实执行结果、数值计算、版本与证据关联、已授权的资源边界 |
| 用户明确选择的范围、要求、评测开关、预算 | 模块拆分、并行程度、局部与全量验证、候选选择 | 原版和用户工作区保护；只取消本任务拥有的进程 |

建议通过标准：遇到新的仓库类型时，agent 能通过组合已有工具推进任务，而无需为了每一个特殊情形修改 Python 状态机。

本次网页只交付设计报告及下载文件。它不会启动重构、恢复之前取消的作业、修改 nanolize 主分支或运行新的模型评测。

## 02 · 当前 main 的具体限制 {#baseline}

**技术栈确认：当前 main 使用 Graphify，已替换旧的 Understand-Anything 输入。** Graphify 的 `graph.json` 提供代码结构、关系和候选社区；nanolize 的 `import_understanding` 导入这些结构证据，agent 审查功能映射并补充语义，随后由 `knowledge-build` / `knowledge-export` 生成供实现 agent 使用的私有知识包。`understanding.py`、`import_understanding` 等名称不表示仍在调用 Understand-Anything。[Graphify 集成说明][main-graphify]、[私有知识包说明][main-knowledge]

Graphify 图不会自动提供全部行为语义；未补充的默认值、异常、兼容和性能约束仍需明确标为未知。首版报告使用“UA knowledge”是术语错误，本版统一改为“nanolize 私有行为知识包”，这不改变本次拟议的调度改造范围。

用户描述的八个步骤是产品层面的概括。当前 `assets/workflow.json` 实际还单列了“保留通过验收的版本”，因此包含九条阶段记录。以下沿用用户的八步分组讨论，避免把界面阶段数量与架构目标混为一谈。

| 现有行为 | 具体代码 | 对不同仓库的影响 | 拆分方向 |
| --- | --- | --- | --- |
| 准备、基线、任务测量、实现、验证按固定分支衔接 | `execution.py::_pipeline()` | 局部环境问题可能阻止无依赖模块继续推进 | 保存机械操作，调度移交 Controller |
| 保留的原版检查未全部通过就拒绝进入重写 | `execution.py::_require_behavior_baseline()` | 原版本身的缺陷、过期依赖与候选回归难以分别处理 | 记录基线失败及比较限制，由 agent 调查与安排后续 |
| 按固定条件选择修复、优化、恢复或结束 | `execution.py::_repair_decision()` | 难以针对失败性质和工作收益调整策略 | 工具返回事实和分类；agent 选择动作 |
| 验证或报告入口可默认触发修复 | `operations.py`、`standalone_repair.py`、`workflow.py::create_run_report()` | 一次“查看结果”可能启动昂贵的代码修改与重测 | 查询、验证、修复、报告分别调用 |
| 出题及原版开发任务测量与重写前置阶段绑定 | `effort.py::prepare_benchmark()` | 即使已有原版快照，也难以灵活安排运行时机 | 拆分任务保存、单次执行、验收与统计 |
| 保存较小的已验收候选，并按固定条件恢复 | `rewrite_stages.py::remember()` 与调度逻辑 | 体积之外的结构、性能、验证质量难以进入选择 | 保存所有可追溯候选，agent 给出选择理由 |
| 代码远端发布受综合成功状态限制 | `execution.py::_pipeline()` 交付段 | 阶段性结果与“完成目标”容易被绑定 | 发布权限、制品生成和验收结论分开；缺口必须显式展示 |

源码依据：[执行调度][main-execution]、[报告入口][main-workflow]、[工具副作用声明][main-operations]、[候选管理][main-stages]、[任务测量][main-effort]。

现有实现已经具备大量可复用能力：隔离工作区、检查执行、失败分类、代码量统计、任务 usage 采集、报告和 Local／Slurm 后端。本次不需要重新实现这些基础能力。

## 03 · 目标架构与职责 {#architecture}

前端输入仍然是“理解仓库 → 选择范围”。中间 Controller 读取用户要求、授权范围内完整可访问的 nanolize 私有行为知识包（agent knowledge） 和已有运行状态，调用工具推进工作。最后 Deliver 消费明确选定的候选和证据，生成原有形式的代码链接与报告。

### 三层职责

| 层 | 负责 | 不应承担 |
| --- | --- | --- |
| Agent 决策层 | 调查问题、选择方法、安排并行、修复、选择候选、解释交付结论 | 编造通过次数、修改实际测量值、擅自降低用户要求 |
| 共享工具层 | 工作区、执行、比较、计量、保存、检索、组合操作 | 在普通查询或报告中隐式启动重写；替用户改变功能范围 |
| 执行适配层 | Local／Slurm 运行、进程与作业归属、状态、取消、结果收集 | 用资源可用性替代功能是否保留的判断 |

CLI、MCP 和网页后台复用同一套工具语义。交互模式下，已有 coding agent 可以直接作为决策方；网页无人值守任务由后台启动 Controller。两种入口应使用相同的工作指导与记录结构，避免无意义地嵌套两个承担相同判断的 agent。

源码访问方式沿用用户授权的实验策略：允许参考原版时可以查源码；明确要求知识隔离时仍需隔离。将流程自主化不应顺便改变这项实验条件。隐藏任务答案的访问隔离同理。

### 必要前置条件与固定顺序的区别

工具可以要求执行自身所需的输入。例如比较需要明确的两个版本，恢复需要确实存在的候选，Slurm 查询需要有效的作业身份。这些是操作语义，不是要求整个项目必须按某条路线执行。

允许一部分模块在基线调查时就开始实现；允许构建与无依赖的源码工作并行；允许先局部检查再扩大覆盖。涉及同一文件的写入应明确归属并串行合并，不能用“并行”掩盖冲突。

## 05 · 工具能力目录 {#tools}

以下是第一版的能力清单：16 项业务能力和 3 项运行管理能力。名称是拟定接口，**并非目前都已实现，也不要求与公开 MCP 工具一一对应**。公开工具应围绕 agent 实际需要的结果确定。

| 类别 | 建议接口 | 主要输入 | 返回结果及边界 |
| --- | --- | --- | --- |
| 契约 | `create_workspace` | 原版或候选版本、用途 | 隔离工作区与来源；不改用户工作树 |
| 契约 | `save_contract` | 功能范围、要求、语义记录及前版 | 契约版本与修改理由；不能降低用户明确要求 |
| 契约 | `capture_baseline` | 原版快照、指定检查、环境 | 实际通过／失败／阻塞结果；失败不抹去已完成项 |
| 重构 | `run_agent` | 职责、输入资料、工作区、允许的工具 | 输出制品、修改、usage、终止状态；不把自述当验收 |
| 重构 | `merge_candidate_parts` | 已完成的模块修改、目标候选 | 合并结果、冲突与重叠；不静默覆盖竞争写入 |
| 重构 | `save_candidate` | 工作区、说明 | 不可混淆的候选身份与来源 |
| 重构 | `restore_candidate` | 本任务的指定候选 | 恢复结果；历史尝试和证据保留 |
| 验证 | `run_checks` | 候选或原版、检查集合、环境 | 退出状态、实际用例结果、日志与未运行项 |
| 验证 | `compare_behavior` | 两侧结果、比较规则 | 可比较范围、差异、基线失败及未知项 |
| 验证 | `check_installation` | 指定构建、安装、使用命令 | 独立安装与使用证据，不以源码目录 import 替代 |
| 验证 | `audit_coverage` | 功能图、检查映射、已有证据 | 直接、间接、缺失或失效覆盖；不推断完整等价 |
| 测量 | `measure_code` | 两侧版本、统计范围 | 行数、tokens、字节及支持的结构指标、排除项 |
| 测量 | `run_benchmark` | 工作负载、环境、运行设置 | 延迟、吞吐、内存等实际记录与比较条件 |
| 任务 | `save_task_suite` | 任务、变体、验收方式、范围 | 可追溯任务版本；任务设计由 `run_agent` 等方式完成 |
| 任务 | `run_task_trial` | 一侧版本、任务、solver 设置 | 修改、实际执行、usage、耗时；验收与解题隔离 |
| 任务 | `compare_task_effort` | 有效验收结果、计量规则 | 成功率、tokens、耗时及波动；缺失 usage 不记零 |
| 管理 | `get_operation_status` | 操作 ID | 运行、等待、退出、结果与清理状态 |
| 管理 | `cancel_operation` | 本任务拥有的操作 ID | 取消结果、已收集证据和资源释放情况 |
| 管理 | `get_run_state` | 本次运行 ID、查询范围 | 候选、契约、证据、未解决问题及活跃操作索引 |

### 建议提供的组合调用

`verify_candidate` 可以执行调用方指定的“检查 → 比较 → 覆盖汇总”，逐项返回结果，不默认修复。`measure_candidate` 可以统一统计源码与配置，生成同口径的前后对比。通用批量调用适合同类、无依赖操作；有依赖的操作按明确顺序执行。

这些组合使用普通函数与显式参数。第一版不发明通用工作流 DSL，不建立为了计划而计划的执行语言。

工具失败应区分：输入错误、缺依赖、资源等待、原版失败、候选回归、检查失效和取消。应携带能帮助下一步判断的信息；建议动作不会被自动执行。

## 07 · 证据、契约与未解决问题 {#evidence}

### 用已有记录承载最小必要信息

建议在现有运行制品之上统一引用，不另建一套庞大的证据平台。每项结果至少能回答：对象是什么、在什么条件下执行、看到了什么、没有看到什么、完整记录在哪里。

| 信息 | 示例含义 | 规则 |
| --- | --- | --- |
| 对象身份 | 原版快照、候选提交、实际源码及配置状态 | 只有 Git 提交相同并不足以证明依赖、资源和运行输入相同 |
| 验证身份 | 检查内容、参数、环境与数据集 | 影响结果的输入发生变化时，旧证据不能自动转成新结果 |
| 证据类型 | 实际观察、程序推导、agent 推断 | 源码阅读可以支持推断，不能替代 GPU 运行或安装成功 |
| 覆盖范围 | 哪些功能、哪些用例、哪些条件 | 多功能检查的映射要准确，父节点不能直接继承“完整通过” |
| 实际结果 | 已通过、已失败、未运行、阻塞、无结论 | 工具退出 0 不自动代表实际执行了非零测试 |
| 结果位置 | 摘要、日志、报告或制品引用 | 默认返回决策所需内容，详细记录按需读取 |

### 契约可以演进，原记录不能被悄悄改写

用户选定范围与硬要求保持有效。若知识描述不足、原测试不适用或环境有误，Controller 可以调查并提出或实施授权范围内的修正。保存新版本及原因；受影响的原版与候选按相同的新方法重新比较。旧失败仍然存在于历史中。

不要求每次编辑都把所有证据重新计算一遍。工具记录关联关系和变化；Controller 判断需要重跑的范围，并说明复用依据。确切版本的观察、复用的历史证据、尚未验证的变化应分别展示。

### 未解决问题的最小结构

问题记录包含：简短问题、影响的功能、当前状态、已知证据、阻塞原因、建议下一步、最近更新。状态可采用 `open / investigating / blocked / contradicted / resolved`。这是实现建议，不是要求新建复杂状态机。

例如“CUDA deform backward 是否保持数值与性能”：CPU 数值测试通过只回答其中一部分，GPU 验证仍待运行。这个问题可以阻塞“CUDA 已验收”的结论，但不应自动阻止其他独立模块的实现。

## 08 · 验收标准与决策边界 {#boundaries}

### 用户要求、评估规则、执行策略分开

| 类别 | 谁决定 | 举例 |
| --- | --- | --- |
| 用户要求 | 用户设定，agent 遵守 | 不删功能、不留空壳、保留防线和类型、不以慢实现换体积、不发明配置 DSL |
| 比较与评估规则 | 工具按明确参数计算；用户指定的规则不可自行降低 | 输出容差、通过检查范围、性能比较条件、任务成本阈值 |
| 执行策略 | Controller 在授权内决定 | 先测哪些模块、何时跑 GPU、如何拆分、局部修复还是整体调整 |

现有与功能保持有关的要求继续沿用：参数校验、可理解的错误、日志和边界处理需要保留；不因功能名字仍在就接受占位实现；源码与配置采用原有可用形式。文档和注释可按既定要求精简，但运行时元数据、类别定义等真实功能数据不能当作文档删除。兼容或遗留内容仅在既定授权和测试依据下处理，不扩大解释为可删选中功能。

代码行数、tokens 和逻辑量作为目标与报告指标，功能保持优先。更少的 AST 节点、SCC 或依赖指标是结构代理，不是行为完整性或认知成本的直接证明。现有分析器不支持的语言与指标保留为未知，不能为了报告完整而估计补齐。

### 严格标准工具化

例如，“指定保留检查全部通过”“独立安装后可用”“没有超过明确容差的性能退步”“任务成本符合选定规则”可以作为具名评估方案。Agent 决定何时调用、如何补齐证据。工具保留失败事实；用户要求的验收未完成时，交付应标注阶段性或有缺口，不能宣称目标已全部完成。

固定流程中技术上不适用的前置阻塞可以移除。用户设定的资源上限、取消请求、实验隔离和权限边界继续由现有机制执行，不因自主化被绕过。第一版不额外加入未经需求支持的停止机制或反作弊系统。

## 09 · 任务成本与运行效率 {#efficiency}

运行时间可能增加。尤其是把每个程序判断改成一次模型调用，或让多个 agent 反复评审已经清楚的问题。预期收益来自更少的无效工作和返工，不来自“有 agent”本身。

下面的拆分用于理解成本，不是可以直接相加的墙钟公式；并行执行和排队存在重叠。

| 成本 | 应记录 | 改进方式 |
| --- | --- | --- |
| 决策 | 模型调用、输入与输出 tokens、等待响应时间 | 一次安排一组工作，按需读取上下文 |
| 工具执行 | 构建、检查、测量的起止时间 | 组合工具、批量操作、复用有效结果 |
| 排队 | Slurm 提交与实际开始时间 | 等待时推进独立模块，分别报告排队耗时 |
| 返工 | 失败原因、重复执行及候选修复 | 改善错误结果与恢复信息，减少盲目重试 |

Controller 的默认指导：优先处理能改变代码或解决关键不确定性的工作；新增评审与验证应有具体理由；没有新证据，不重新讨论已解决问题；不能把反复撰写计划当作完成重构。给出默认路线，同时允许根据仓库调整。

第一版优先优化摘要质量、组合调用、结果复用和并行等待。动态工具目录、自动选择复杂策略和额外调度框架暂不引入。工具更少不保证总 tokens 更少，应统计整个任务的调用和重试。

### 任务评测的自由与实验有效性

保存不可变原版快照后，原版测量可以在合适的时候运行，不必全部先于实现完成。任务设计与答案隔离仍需与结论一致：看过候选后专门挑选的任务只能作为针对性分析，不能宣称是独立隐藏评测；重复向实现方反馈隐藏结果会改变实验性质。

用户关闭评测时，不设计或执行这些任务，也不宣称任务成本改善。开启时，记录解题成功率、同口径 usage、模型与环境设置、重复次数、失败和波动；Controller 本身的调度成本与 solver 比较成本分别展示。缺失计量不是零成本。

## 10 · 三个运行情景 {#scenarios}

以下均为解释新调度方式的示例，不是已执行的实验结果，也不是强制路线。

### A. 简单 Python 库

读取范围与现有检查 → 一次建立可用基线 → 一次结构调整 → 组合验证 → 记录指标并交付。没有充分理由时不启动多轮评审、不设计额外 GPU 验证、不拆成大量 agent。目标是使普通路径的额外调度开销保持较小。

### B. 包含 CUDA 与旧后端的大仓库

原版 CUDA 编译与独立 Python 模块实现并行；把旧后端缺依赖记录为单独问题；先验证可运行部分，安排 GPU 作业后继续源码工作。需要交付对应功能时补齐相关证据。不能为了达到压缩目标删掉 CUDA 实现或把未验证的旧后端标成通过。

### C. 原版检查本身失败

保存原版失败 → 调查是环境、测试还是原版缺陷 → 对无依赖功能继续工作 → 如需修订检查，记录版本与理由 → 在原版和候选执行同一新检查。若无法获得可比较基线，报告该功能的证据缺口；不能将候选也失败直接解释为功能完整。

三个情景应使用同一工具集。差异主要体现在 Controller 的计划、工具参数及证据解释，不应通过三个新的硬编码执行模式实现。

## 11 · 实施顺序与迁移 {#rollout}

| 阶段 | 交付内容 | 验收重点 |
| --- | --- | --- |
| P0 · 对齐接口与事实 | 固定当前基线，列出被拆函数、默认副作用、输入输出与已授权边界 | 每项变更可定位，不把设计当成已实现 |
| P1 · 提取工具 | 独立验证、测量、候选操作；报告只读；建立共享返回结构 | 同样输入得到与原能力一致的真实结果，失败不抹去部分数据 |
| P2 · 接入 Controller | 共享工具调用入口、可选工作指导、问题列表、批量与异步使用 | 可处理不同执行顺序，模型只负责策略而非计算统计值 |
| P3 · 接续与交付 | 网页后台接入、运行恢复、进度、既有功能图报告与发布 | 新候选绑定新证据；历史运行可读；中断不重做无关工作 |
| P4 · 对照与收敛 | 常规仓库、编译仓库、异常基线仓库的同条件比较 | 功能结果、实际成本与失败原因均可审查，再决定默认切换 |

迁移期间，不把正在运行的旧任务偷偷换成新 Controller。历史记录继续可读；新运行使用明确的新执行方式。旧任务若要迁移，应显式记录运行版本和可复用制品，不能伪装为原流程无缝继续。

最终目标是一套共享核心能力与新的默认自主路线。为迁移而保留的旧入口不应长期发展成第二套平行维护的策略系统。移除旧代码前检查 CLI／MCP、后台恢复和历史报告消费者。

## 12 · 测试与成本对照计划 {#validation}

### 工具及集成验收

| 检查 | 需要证明什么 |
| --- | --- |
| 验证、报告无隐式实现调用 | 查询和渲染不会修改候选，不触发修复 agent |
| 部分检查失败或取消 | 已完成的结果保留，未执行项不能成为通过 |
| 契约、检查版本调整 | 原版与候选比较引用一致，历史失败可追溯 |
| 候选、依赖或资源变化 | 不能沿用旧通过结果冒充当前版本的新观察 |
| 功能范围与 task-effort 开关 | Controller 无法自行删除范围或开启明确关闭的评测 |
| 工作区、恢复与并行合并 | 不覆盖用户工作树，文件冲突有明确处理 |
| Local／Slurm 状态与取消 | 只操作属于本任务的资源；作业退出与应用仍在运行可区分 |
| CLI／MCP／网页后台 | 相同能力语义一致，界面只映射事实 |
| 报告和安装验证 | 下载内容完整，功能图不扩大覆盖；安装检查确实在安装环境使用 |

工具正确性测试使用假的 agent 或受控 stub，避免单元测试调用真实模型。实际 Controller 行为必须另行做真实任务实验；脚本化调用序列不能证明 agent 会正确选工具。

### 对照实验

选择三类代表仓库：小型纯 Python 库、具有原生扩展与 GPU 的仓库、原版检查或依赖存在实际问题的仓库。固定源码版本、功能范围、模型及推理设置、任务评测开关和可比较资源条件。记录缓存状态，重复观察，不用单次结果得出普遍速度结论。

对比旧 main 与新方案的：总墙钟时间、执行和排队时间、全部 agent tokens、缓存与非缓存输入、功能验收结果、未验证范围、返工次数、人工介入及代码指标。复杂仓库的收益可以体现为更少阻塞和人工处理，不必要求每个样本都更快。

性能和压缩收益目前均为**待测量**。本设计不承诺固定加速比例、tokens 降幅或达到某个压缩率。若新方案变慢，应先定位是模型往返、工具设计、重复验证还是资源等待，再调整，不通过省略必要功能验收制造速度优势。

## 13 · 第一版范围与暂缓项 {#scope}

第一版必须包括：中间调度交给 agent；基础与组合工具；取消默认隐式修复；简明结果及证据引用；未解决问题列表；共享 CLI／MCP 语义；保持输入输出体验；运行恢复与真实计量。

暂缓：大型工作流 DSL、通用插件市场、动态工具发现、复杂知识图数据库、自动策略训练、把 REA 的整个资源管理系统搬入、为所有工具都强制安排独立评审。

沿用已有配置，不增加用户必须逐个选择工具或审批中间步骤的负担。内部默认可以提供常规指导、检查组合和简短摘要；它们不能重新成为阻止 agent 调整路径的固定状态机。

最重要的实施检查：新增代码是否真正减少了固定策略与隐式副作用；新增提示词是否帮助判断而非重复规定死顺序；新工具是否一次提供足够信息；报告是否忠实表达尚未完成的目标。
