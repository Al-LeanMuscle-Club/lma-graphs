01 / START FROM WHAT WORKS

保留 main 的主线，补上受限的判断能力。

main 的重写和修复本来就由 Agent 完成；固定的是调度规则。新方案保留这些规则，在证据表明原路径可能无效时，才咨询 Controller。

这次设计的完成标准，不是“Controller 能跑起来”。

需要证明普通任务没有新增模型决策开销，复杂任务的介入产生了可验证的收益。代码量、速度、模型 tokens 和验收质量分别呈现。

为什么重做调度：既有实验给出的信号 ＋

tqdm 实验中，Controller 的 13 次决策累计约 3.31M tokens、23.6 分钟；功能通过后的四次体积优化另用了约 10.96M tokens、57.2 分钟。决策成本与选择继续执行的成本是两类问题。

Main 那次拥有更完整的初始规格：114 条契约，对比 Controller 初始的 104 条。Main 还有一次中断调用的完整用量缺失，因此不能将这组结果视为严格同条件的引擎性能结论。

03 / FILE-BY-FILE CHANGES

具体改哪里，为什么改，怎么验收。

以下 11 组变更覆盖调度、决策、预算、报告和验证。新增文件名与参数属于设计建议；已有模块链接固定到本页核对的 main 提交。

第一版将 Controller 的作用限定在下一次修复或停止判断。多工作区并行实现与多方案搜索可作为后续独立实验，先验证最小介入是否值得。

04 / DECISION CONTRACT

能建议什么，与何时执行，是两件事。

模型提供建议，程序核验证据、当前版本、修改范围和剩余预算。一个建议只作用于当前决策边界。

情形拟议处理关键约束
第一次普通回归按 main 修复，不调用 Controller保持现有相关能力筛查和最终全量验收
连续两轮同类失败，无可见进展预算允许时咨询一次同时比较细节和范围，不只比较检查组数量
修复反复引入相关回归考虑策略调整或恢复候选只能恢复本任务生成代码，恢复后重新验收
有证据的规格缺口整理具体缺口或提出下一步建议请求不等于授权；不自动执行新增命令
原版失败、环境缺失、未运行保留未验证／阻塞不直接当成候选代码错误
冻结输入完整性异常按原规则停止模型建议不能覆盖这个判断

05 / BUDGETS & ACCOUNTING

介入有独立预算，支出不会因重启消失。

决策预算与 Author 修复预算分别记录。Controller 建议进行代码修改时，仍使用原有 Author 次数和作业期限。

拟议参数实验建议值约束方式
controller_modeauto / offauto 按需介入；最终默认值由性能验收决定
最大决策次数2 次 / 任务硬限制；已开始的中断调用也保留记录
决策时间单次 60 秒；累计 120 秒受剩余作业时间共同约束
决策 tokens累计 200K按可观测用量控制后续准入；不能假设所有 runner 都支持实时精确截断
Author 与任务评测沿用原配置不因 Controller 介入而增发预算

预算规则演示

仅为设计演示

调整“已消耗”的数值，查看下一次决策是否可启动。数值不会保存或改变实际任务配置。

时间、次数可以硬停；token 限额必须说明计量能力。

如果 runner 只在结束时返回 usage，单次调用可能超过剩余 token 预算。收到结算后禁止继续启动下一次；用量缺失不按零处理。即使有流式用量，也应记录事件延迟和实际超额。

每一次调用都留下收据

按调用 ID 记录角色、开始／结束、输入、缓存输入、输出、完整性与退出原因。缓存输入属于输入子集；分角色计时不能冒充总墙钟。

恢复继续同一本账

累计决策成本不清零，已完成操作不重复结算，过期建议重新校验。取消释放本任务的进程与资源，候选和历史证据继续保留。

06 / THE MERGE STANDARD

“性能成为合并标准”，具体意味着什么。

Controller 改动合入 main 前，除了功能正确，还要证明没有稳定的流程效率退化。这里衡量 nanolize 的耗时和模型用量；压缩后程序的运行性能单独验证。

不让每个用户任务都多跑一遍 main。

性能对照发生在开发、准备合并和后续回归阶段。真实模型实验按明确预算执行，普通 CI 使用离线 runner 验证确定性行为。

A

冻结 main

原始基线，固定提交和输入。

B

新版本 · off

检查基础改造和计量本身的开销。

C

新版本 · auto

观察按需决策是否创造实际收益。

实验条件必须一起冻结。

输入

原始提交、知识包、功能范围、体积要求、验收与隐藏任务。

执行

模型版本与设置、预算、环境、资源、任务重复配置。

计量

起止时间、排队口径、所有角色与失败调用、缓存和用量完整性。

顺序

三组交错、多次重复；不把另一组发现的新规格只补给后跑的一组。

拟议实验矩阵与判定方式 ＋
场景主要问题验收重点
首次实现即可通过是否无故增加开局／收尾决策0 次 Controller；同等验收
一次普通修复是否过早介入沿用原修复；最终全量验证
重复同类回归一次建议能否减少后续无效尝试完整披露修复次数、成本、最终结果
原版失败／环境缺失是否误把未验证当代码错误状态正确；不得通过少验收取得“胜出”
预算／取消／恢复是否继续耗费或丢失记录边界生效，账本连续，候选可追踪

建议首轮每个真实场景至少 5 次重复，临界结果增加样本。少量重复只能提供初步证据；不能声称某个 tail percentile 已稳定。

容差、样本量与合并判据应在看到结果前确定。当前方案尚未设定最终数值门槛：先测基线波动，再预先登记容差；不能在看到退化后扩大容差。

以全部运行报告完成率和支出，并对同等验收质量的结果比较成本。提前失败的低成本不能当成优化成功；Main 失败而 auto 完成时，应报告成功率收益与额外成本，而不是无条件宣称更快。

严格保证每一次随机运行都更快、更省并不现实。可落实的目标是：普通路径不增加模型决策，复杂路径的收益经公平对照证明。

07 / IMPLEMENTATION ORDER

先把成本看清，再决定默认启用。

第一版围绕最小介入完成闭环。每一阶段都有可检查的退出条件，避免“能够自主调用工具”代替“改造有效”。

完成后应交付什么

  • 基于冻结 main 的新分支与可审阅差异。
  • 受限决策接口、配置、预算和恢复记录。
  • 所需回归检查结果与公开安全的报告字段。
  • main / off / auto 的公平对照及是否启用的结论。

哪些仍需实验决定

  • 连续停滞的阈值与误触发率。
  • 2 次、60／120 秒、200K 是否合适。
  • 简短上下文是否足以提出有用建议。
  • auto 的默认启用范围及性能容差。
如果普通路径多了一层模型调用，或者复杂路径只是多尝试几轮却没有证据收益，这一版就没有达到本方案的设计目标。
