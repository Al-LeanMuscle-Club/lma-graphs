04 / VALIDATION EVIDENCE

每个完成标记，都有对应检查。

验证使用真实 Git 工作区、子进程和浏览器；模型执行器采用显式离线脚本，测试本身不会启动付费模型调用。

取消与恢复

  • 决策启动前持久化调用预留；中断后费用不消失。
  • 恢复后保留独立预算，不重复咨询同一状态。
  • 已验证的交付阶段重放，不重复调用 Author 或 Controller。
  • 直接用原 main 创建旧任务，再由新版本恢复。

质量与公开边界

  • 完整验收、冻结输入和能力范围继续生效。
  • 粗粒度组内细节改变，不误判为停滞。
  • 公开报告只呈现枚举和计数，过滤私有路径与指令。
  • 新提示词进入 wheel，并在独立安装环境加载。

通过这些检查证明相关执行路径符合预期，不代表已证明任意仓库的全部语义等价。

MCP／Python 使用 adaptive_controller 对象；可附加 owner 固定的 runner、model 和 reasoning 配置。

它不增加原预算

Controller 建议进行修复时，Author 仍消耗原有次数和作业期限。保存、计数、状态查询和收尾由程序完成。

次数和时间限制控制后续准入及终止请求。只在结束时提供 usage 的 runner 可能单次超额；进程清理也会增加墙钟。系统记录实际消耗，不假装能够实时精确截断 tokens。

新报告字段含义
Author / Controller / Task evaluation分别报告模型调用次数、输入、缓存输入、输出与完整性。
缓存输入输入 tokens 的子集，不再叠加到总量。
用量未知或部分记录保留 observed subtotal，真实总量为未知；不写成 0。
角色时间与作业墙钟角色执行可能重叠，不能简单求和当成总耗时。
触发、动作、下一轮结果记录为什么介入、实际接受的动作，以及后续证据是否改变。
07 / WHAT REMAINS BEFORE DEFAULT AUTO

性能成为合并标准，还需要真实实验。

“实现完成”与“足以默认启用”是两个不同结论。本分支交付了验证工具与关闭开关，尚未交付真实模型效率胜出的结论。

  1. 先登记比较条件与容差。

    冻结源代码、知识包、模型、功能范围、任务与验收、环境和预算；先测基线波动，不能看到退化后扩大容差。

  2. 进行多次配对运行。

    比较 main、off、auto，初步每场景至少五次；交错顺序，临界结果增加样本。少量重复不能支持稳定尾部耗时结论。

  3. 同时看质量、完成率和总成本。

    包括失败与中断的支出。只有同等质量下的成本才可直接比较；提前失败的低成本不算优化成功。

  4. 有证据后再决定默认值。

    普通路径零额外模型调用只是必要条件。复杂任务要证明介入值得，再考虑合并并默认启用 auto。

后续范围仍然受限。

多工作区并行实现、多方案搜索，以及把整个流水线交给 Controller 调度，都没有加入这一版。
