本次新发现 · Feedback Memory

嵌套 schema 多了原版没有的限制

对 list[Annotated[int, Field(ge=1)]]，原版生成的元素 schema 只有 type: integer；Feedback 增加了 minimum: 1。默认 Field 的优先级已经一致，但嵌套项仍不同。

原始仓库 / Auto50 Review
{"items": {"type": "integer"}}
Feedback / 两个 Core49
{"items": {"type": "integer", "minimum": 1}}

对功能保留任务，这个“增强约束”会改变模型接收的 schema，不能直接算作兼容性改进。它不在本次原有 12 组验收中，因此此前的通过记录仍成立，但不能扩展为全面等价。

平台引擎 / 头文件＋generation 3 权重→完整部署目录

数值提取探针也显示旧分支在 8 个输入中有 5 个与原版不同，例如 12,34、5.25x。这是内部 grounding 辅助函数的边界观察，不应泛化为所有公开提取调用都会失败。

05 / 实验轨迹

每次重写，究竟花在了哪里

以下是实验运行时记录，不是今天复测的结果。“暂缓”指修复筛查没有运行某组，不等同于新增失败。Feedback 中途增加了一个已在原版验证的边界检查组，因此验收组数从 11 变为 12。

重复修复会消耗 tokens，但轨迹长度本身不代表质量

Core49 的第 5 次调用没有产生新代码；Tasks 的开发评测虽然完成，仍没有取得成本改善证据；Auto50 在任务评测后修改了交付代码；Feedback 的后 3 次作者调用主要服务于补充契约。把这些调用都称为“体积优化”，会误判时间花在了哪里。

06 / 结构与可读性

更短的代码，不自动等于更好维护

对固定提交重新做 Python AST 与词法扫描，并人工阅读运行入口、工具 schema、worker、native 与 CLI。下面是结构事实，不是主观评分。

¹ 行数按原始文件文本行统计，包含空行和注释，仅用于理解结构与排版；本报告的压缩规模指标仍为 tokens。函数跨度含函数体中的空行、注释与嵌套定义。

两个 CORE49

文件少，入口模块承担更多职责

均为 9 个 Python 文件，needle/__init__.py 分别为 542 / 565 行，混合原生运行与 grounding 逻辑。共享的 _native.py 与 _worker.py 已经拆出；并非将全部逻辑堆成一个文件。

两者没有分号拼接语句，也未发现直接调用 eval / exec / compile。Core49 在四者中源码 tokens 最少，但历史修复成本最高，新增兼容性检查仍有缺口。

AUTO50 / FEEDBACK

grounding 独立，模块边界更清晰

分别将 _grounding.py 拆出为 190 / 218 行；入口缩为 376 / 395 行。Auto50 另有一个 4 行的 worker 启动模块，11 个文件不意味着逻辑更多。

Feedback 的 CLI 为 123 行，较旧版本 80～96 行更长，覆盖了额外的下载和诊断行为。其工具 schema 实现仍有前文发现的差异，清晰结构不能替代行为验收。

逐文件规模与固定源码链接＋

四个版本均调用真实外部引擎 / 权重；它们是共同运行依赖，不计入 Python 源码压缩量。静态扫描没有发现直接动态执行调用，但这不是安全审计，也不代表穷尽所有间接执行方式。长行数量只描述排版，不单独判断可维护性。

07 / 后续任务成本

压缩后，Agent 做修改任务更容易了吗？

只有两次历史实验开启了独立任务评测，每个阶段每个版本只有一次观测。任务是工具 schema 的修改工作流；不能推广为所有理解、诊断、执行、修改任务的平均表现。

Core49 + Tasks：未建立改善证据

原版 / 候选各完成一次开发任务，tokens 为 273,083 / 273,551，候选高 0.17%；耗时 282.3 / 322.5 秒。结论为“不确定”，隐藏任务没有运行。这个任务结果绑定最终提交 4b35478c。

此前一次任务检查因执行器继承 future annotations 改变语义而作废。执行器修复后重测双方，原任务定义保持不变；作废部分不参与收益比较，但其时间与用量保留。

Auto50：旧版本隐藏任务成本回归

开发任务 tokens 下降 18.14%，隐藏任务却增加 36.34%。四次有效解题的可执行验收都通过，失败的是成本门槛，不是这些任务的功能验收。

这些记录只属于 cd684596。交付的 d266be7e 此后修复了 schema，没有再次运行任务评测。因此最终分支的任务成本应标记“未验证”，而不是沿用旧版本的回归或改善结论。

本次的回答是“尚未测量”

Feedback 按本次指令优先简洁可读的 core 实现，在功能 / 安装验收后停止，未开启任务成本评测。代码更小、生成更快，都不能单独证明后续 Agent 维护会更省 tokens。Core49 同样没有这方面数据。

08 / 差异解读与下一步

看见改进，也保留因果判断的边界

有证据支持的判断

这次交付更高效，但并非严格 A/B

本次作者调用合计 20.7 分钟 / 285.6 万 tokens，低于三个旧实验的 31.8～73.1 分钟 / 527.0～1,032.5 万 tokens。第一版就通过共同的 11 组检查，也减少了早期基础行为返工。

与此同时，输入知识契约从早期的 774 条演进到本次初始 999 条，且吸收了先前原仓库语义澄清；本次还关闭了任务评测。这些变化与 Controller 同时发生，现有记录无法分离各自贡献。

接下来最值得做的三件事

先补齐回归，再验证收益

  1. 把兼容性补丁沉淀成共同验收。补齐 Feedback 的嵌套 schema 语义；保留 CLI 权重、Field 优先级与数值边界用例。当前分支在本次对比中没有被修改。
  2. 做真正的开关对照。固定同一知识包、模型 / effort、目标、执行资源和验收；仅切换 Controller / feedback memory，每组多次重复，报告完成率与时间分布。
  3. 分开衡量生成与维护。记录含缓存用量、非缓存输入、输出及实付成本；另设独立任务评测，绑定最终代码提交，不把补修前的成绩沿用到补修后。
计量范围、证据边界与尚未覆盖的内容＋

时间

优先使用第一次提交到最终功能 / 安装验收或流水线终态的记录跨度。Core49 与 Feedback 没有跨运行恢复；Tasks 与 Auto50 包含此前失败和恢复。时间包括调度和宿主等待，不含提交前环境、知识包准备，也不含报告发布。报告制作与这次 1 分 48 秒的复测不混入历史实验耗时。

模型用量

累计实验实际 spawned CLI 的 usage，失败 / 作废调用只要有用量也计入。输入 tokens 已含缓存；输出已含推理输出，均不重复相加。外层协调 Agent、人工式源代码审查、知识补充及报告制作没有完整用量账本，故标记“已观测”而非全链路总成本。

验收

同一套已冻结检查，原始仓库先通过所有 13 组，再比较候选。共同 pytest 用例数 105；安装独立为 3 项。CLI 下载替身隔离网络，真实推理使用共同 native 资产。所有被测代码与原始检查输入哈希在运行前后保持不变。

局限

单次历史实验、知识输入不同、早期作者模型未冻结；无法作统计性优劣判断。没有覆盖全部原始功能、全部边界输入、所有操作系统 / 设备或长时间并发。source-free 作者输入是一种工作流约束，原始 source 没被提供给作者，但共享文件系统不是 OS 级隔离。
