TQDM / THREE INDEPENDENT RUNS

压缩得更小，
是否也做得更好？

对比 Main、Controller 与 Feedback memory。把最终代码、生成过程和付出的成本放在同一张图上，也把旧验收没有发现的问题重新拿出来检查。

观察结论

Main 最小、耗时最短。 Feedback memory 补齐了更多兼容性细节，但更耗时，也仍有 CLI 输出流回归。三个最终版本均保留了原始源码的 59%—61%，没有一个达到“源码本身低于 50%”。

06 / METHODOLOGY

哪些可以比较，哪些不能直接归因

共同基础

  • 同一原始提交 9cf5a12b1f95。
  • 全部 27 项功能选择，没有主动排除功能。
  • tiktoken 0.12.0 / cl100k_base，逐文件独立编码后求和。
  • 原始源码与配置分母一致：45,979 / 26,169 tokens。
  • 最终发布树与当时验证的代码树一致；本次比较没有修改三个分支。

关键差异

  • Memory 额外要求源码本身低于 50%，并新增两组功能检查。
  • Main 使用预先冻结的题目；另外两次包含模型出题。
  • 任务预算、配置重复次数、优化额度、环境和监督干预不同。
  • Memory 直到中途才获得精确的本地源码 token 计数工具。
  • 每种流程只有一次独立运行，不能隔离 memory 功能的因果作用。
计量规则与未覆盖范围

代码大小

沿用每次运行冻结的分类规则：未修改的原始测试、文档和二进制资产被排除，修改后的文本仍计入。原始 notebook 测试及其 nbval 配置在该分类器下属于配置，三个实验均包含这部分固定的 4,291 tokens。物理代码行数不作为验收指标。

模型用量

总量 = 输入＋输出，缓存输入是输入的子集，只计算一次。“未缓存输入＋输出”也不是费用：它没有应用输入、缓存和输出的不同计价。本报告不估算美元费用。

    07 / IMPLICATIONS

    下一轮，先让验收与迭代更可靠

    本次证据不支持“加了 Controller 或 memory 就一定更好”。更有价值的改进，是把已经发现的问题固定下来，并减少低收益的重复工作。

    01

    建立跨运行的共同验收

    把模板、流包装接口、range、真实 argopt 和 CLI 输出流检查合并成共享套件。所有策略使用同一目标和同一原始契约，再比较质量与成本。

    单次运行记得修复，不等于下一次运行不会再犯。
    02

    保留草稿与可执行的修复记忆

    明确允许复用本次生成的候选代码，记录问题、修复、绑定版本和回归检查。避免把“独立实现原始功能”误解为每次修复都重新实现。

    Main 的中断恢复说明这个问题确实发生过。
    03

    给优化设置边际收益停止条件

    从第一轮提供精确计数；根据连续轮次的净收益、实际调用成本和引入回归的情况决定是否继续。小幅减少代码不应自动触发无限迭代。

    Memory 六次优化调用消耗 14.259M tokens，最终源码净减少 650 tokens。
